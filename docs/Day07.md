# Day 07 - Detection Engineering and Correlation Rules

## Objective

Learn how to tune Wazuh detection rules by reducing alert noise using correlation rules, severity tuning, and threshold-based detection.

---

# Concepts Learned

## Detection Engineering

Detection engineering is the process of creating, tuning, testing, and improving security detections to identify malicious activity while minimizing false alerts.

---

## Alert Fatigue

Alert fatigue occurs when analysts receive too many alerts, making it difficult to identify genuine threats.

Example:

A user logs in successfully every morning.

Generating an alert for every login would create unnecessary noise.

---

## False Positives

A legitimate activity that is incorrectly identified as suspicious.

Example:

A system administrator logging into a server.

---

## False Negatives

A malicious activity that is not detected by security monitoring.

Example:

An attacker successfully authenticates without triggering any alert.

---

## Severity Levels

Wazuh assigns a severity level to every alert.

Lower levels indicate informational events.

Higher levels indicate more critical security events.

---

## Correlation Rules

Correlation rules combine multiple related events into a single meaningful alert.

Instead of alerting for every individual event, Wazuh waits until a defined threshold is reached.

---

## frequency

Specifies how many matching events must occur.

Example:

frequency="5"

means:

Trigger only after five matching events.

---

## timeframe

Defines the time window for the matching events.

Example:

timeframe="60"

means:

The five matching events must occur within sixty seconds.

---

## if_matched_sid

Instead of matching a base rule directly, Wazuh monitors previous alerts generated by another rule.

Our custom rule monitors:

Rule ID 5715

which detects successful SSH authentication.

---

# Practical Tasks

## Modified Existing Custom Rule

Changed alert severity.

Before:

level="7"

After:

level="3"

Reason:

Successful SSH logins are informational and should not create high-severity alerts.

---

## Converted Rule into Correlation Rule

Before:

<if_sid>5715</if_sid>

After:

<if_matched_sid>5715</if_matched_sid>

Added:

frequency="5"
timeframe="60"

This created a threshold-based detection.

---

## Configured SSH Key Authentication

Generated an ED25519 SSH key pair.

Copied the public key to the Ubuntu server.

Verified public key authentication.

This allowed automated testing without repeatedly entering passwords.

## Tested Detection

# Troubleshooting

Issue 1

Problem:

Permission denied while loading local_rules.xml

Cause:

File ownership changed to root:root after copying into the Docker container.

Resolution:

Changed ownership back to:

wazuh:wazuh

---

Issue 2

Problem:

Invalid use of frequency/context options.

Cause:

frequency and timeframe require if_matched_sid instead of if_sid.

Resolution:

Replaced:

<if_sid>

with

<if_matched_sid>

---

Issue 3

Problem:

SSH still requested a password.

Cause:

Public key authentication was not being used.

Resolution:

Verified SSH keys.

Compared public keys.

Verified SSH configuration.

Confirmed successful authentication using:

Accepted publickey

---

Issue 4

Problem:

Dashboard still displayed the old alert description.

Cause:

Older alerts retain the description that existed when they were generated.

Resolution:

Restarted Wazuh Manager.

Generated new events.

Verified the newest alert displayed the updated description.
